# ASIScan — growth engine

An autonomous content and distribution system. It publishes a technical blog
post a week to `asiscan.dev/blog`, posts to the LinkedIn company page, rescans a
corpus of open-source AI agent repositories every month to keep its statistics
real, and sends one digest a week.

It is designed to run without you. Your total ongoing involvement is reading a
digest issue on Sunday, which takes about a minute, and adding topics to a JSON
file when the queue runs low.

---

## The idea it is built on

Autonomous content usually fails for one reason: a language model with nothing to
say will produce fluent nothing, and for a *security* product fluent nothing is
worse than silence.

So the model here is never the source of a fact. The scanner is.

```
  corpus of 50 open-source agent repos
              │
              ▼  scan-corpus.mjs (monthly)
    data/corpus-findings.json          ←── the only place statistics come from
              │
              ▼  generate-post.mjs (weekly)
     a draft, written from measured data + a verified claims ledger
              │
              ▼  fact-guard.mjs
     every number traced, every banned phrase blocked, disclaimers required
              │
       ┌──────┴───────┐
   publish          compose-social ──▶ LinkedIn company page
```

`fact-guard.mjs` is the part that replaces you. If the generator produces a
number that does not trace back to a scan result or to `config/claims.json`, the
post does not ship. It fails closed. A quiet week costs nothing; a wrong claim
about a security framework costs the positioning.

## Setup

One-time, about 45 minutes. Steps 1–4 are required; the rest are optional.

### 1. Create the repository

```bash
gh repo create asiscan-growth --private --source . --push
```

### 2. Point Vercel at it

The `site/` directory is the deployable root. In the Vercel project for
`asiscan.dev`:

- connect this repository as the Git source
- set **Root Directory** to `site`
- framework preset: **Other**
- build command: leave empty (the HTML is committed)

Copy your existing `index.html` and `thanks.html` into `site/` before the first
deploy so the landing page keeps working. The blog lives at `site/blog/` and is
regenerated by `npm run build`.

### 3. Secrets and variables

Repository → Settings → Secrets and variables → Actions.

**Secrets**

| Name | Required | What it is |
|---|---|---|
| `ANTHROPIC_API_KEY` | yes | Content generation. Budget roughly a few dollars a month at one post a week. |
| `BUFFER_ACCESS_TOKEN` | for LinkedIn | See step 4. |
| `BUFFER_LINKEDIN_CHANNEL_ID` | for LinkedIn | The channel ID of the connected company page. |
| `VERCEL_TOKEN` | optional | Puts traffic numbers in the weekly digest. |

**Variables**

| Name | Default | Notes |
|---|---|---|
| `ANTHROPIC_MODEL` | `claude-sonnet-4-5` | Set explicitly so a model deprecation is a settings change, not a code change. |
| `SOCIAL_MODE` | `llm` | `template` for deterministic, model-free social copy. |
| `SOCIAL_TRANSPORT` | auto | `buffer`, `linkedin` or `webhook`. |
| `BUFFER_MODE` | `queue` | `now` publishes immediately instead of queueing. |
| `SCANNER_CMD` | `npx --yes asiscan-cli@latest` | npm refused `asiscan` as too similar to `asi-scan`. | |
| `PAUSE_PUBLISHING` | unset | Set to `true` to stop everything. |
| `VERCEL_PROJECT_ID` | — | For the digest. |

### 4. Connect LinkedIn

The direct LinkedIn API is not a realistic path for this. Posting to a company
page requires their Community Management API, which requires a registered legal
entity plus an approval process that runs weeks to months, and it is not
guaranteed. Do not block on it.

Use Buffer instead. Buffer already holds LinkedIn partner approval, so you
connect the page once as its admin and never touch LinkedIn's developer portal.

1. Create a free Buffer account and connect the ASIScan company page as a channel.
2. Create an API token in Buffer's developer settings.
3. Find the channel ID (`GET https://api.bufferapp.com/2/profiles.json`).
4. Put both in repository secrets.
5. Run the **Publish to LinkedIn** workflow manually with `dry_run` on, confirm
   the copy looks right, then run it with `dry_run` off once to prove the path.

If you later get Community Management API access, set `LINKEDIN_ACCESS_TOKEN`
and `LINKEDIN_ORGANIZATION_URN` and the code switches transport with no other
change. `scripts/refresh-linkedin-token.mjs` handles the 60-day token rotation.

**One honest caveat.** LinkedIn's developer AI policy says applications should
not publish AI-generated content without giving a person the chance to edit it
first. It is written for multi-tenant apps, and scheduling your own company's
posts through a scheduler is ordinary permitted use — but a fully unattended
generate-and-publish loop sits closer to that line than a scheduled queue does.
Two things keep this on the safe side of it: `BUFFER_MODE=queue` puts posts into
a scheduler rather than firing them, and `SOCIAL_MODE=template` removes the model
from social copy entirely. If you ever want to be conservative, set
`SOCIAL_MODE=template`; the blog stays fully generated either way, and your own
website is not subject to anybody's platform policy.

### 5. First run

```bash
npm ci
npm test                      # 15 tests, all should pass
npm run scan                  # ~20 min, populates data/corpus-findings.json
npm run generate -- --dry-run # prints a post without committing anything
npm run build && npm run guard
```

Then run the **Publish content** workflow manually once. After that it is on a
schedule and you can leave it alone.

## Schedule

| Workflow | When | What |
|---|---|---|
| `publish.yml` | Tuesdays 09:00 ET | Generate → verify → build → commit → queue the LinkedIn post |
| `social.yml` | Tue 09:30, Thu 10:00 ET | Drain one item from the social queue |
| `corpus-scan.yml` | 1st of the month | Rescan the corpus, refresh every published statistic |
| `digest.yml` | Sundays 09:00 ET | Open one issue summarising the week |
| `guard.yml` | every push and PR | Nothing bypasses the fact checks, including you |

Everything also runs on `workflow_dispatch`.

## The kill switch

Two ways, either works instantly:

```bash
touch PAUSE && git commit -am "pause publishing" && git push
```

or set the repository variable `PAUSE_PUBLISHING` to `true`.

Every publishing workflow checks both before doing anything irreversible.

## What you actually maintain

**Weekly (1 minute).** Read the digest issue. If it says a draft was rejected,
that is information, not a fire — the topic retries next week.

**When the queue runs low (10 minutes, roughly quarterly).** Add topics to
`content/topics.json`. The digest warns you at four remaining.

**When you learn a new verifiable fact about the product (2 minutes).** Add it to
`config/claims.json` with its source. This is the only way a new number becomes
publishable, and it is deliberately a small amount of friction.

**When something reads wrong.** Edit `config/voice.md`. It is fed verbatim into
every prompt and takes effect on the next run.

## Layout

```
config/
  brand.json      product name, domain, pricing — single source of truth
  claims.json     the claims ledger; verified facts, blocked claims, banned phrases
  voice.md        tone guide, fed into every prompt
content/
  topics.json     the backlog; first pending topic is next to publish
  published/      generated posts, source of truth for the blog
  rejected/       drafts that failed verification (never published)
corpus/
  repos.json      the 50 repositories scanned for research statistics
data/
  corpus-findings.json   the only permitted source of statistics
  corpus-history.json    trend data for quarterly comparison posts
  social-queue.json      composed LinkedIn posts and their status
scripts/
  scan-corpus.mjs        the data engine
  generate-post.mjs      draft → verify → publish, or fail closed
  build-site.mjs         markdown → HTML + RSS + sitemap
  compose-social.mjs     LinkedIn copy, template or model, always verified
  publish-social.mjs     Buffer / LinkedIn / webhook transport
  digest.mjs             the weekly issue
  guard-cli.mjs          runs fact-guard over everything
site/                    deployed to Vercel
```

## Research ethics

The corpus scan produces findings about other people's open-source projects.
Three rules, and the workflows and prompts enforce the first two:

1. **Aggregates only.** Never publish a per-repository finding list. Never rank
   projects by findings.
2. **A static finding is a signal, not a vulnerability.** Framework repositories
   will legitimately show control-probe findings for controls that belong to the
   application calling them. Say so, every time.
3. **Disclose before you publish.** If a scan surfaces something that looks
   genuinely exploitable in a specific project, report it privately to the
   maintainers and give them a reasonable window before any related post goes
   out. In security, how you handle this is itself the reputation.
